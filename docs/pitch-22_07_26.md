# Commodity Cloud
## Turning the devices in your drawer into infrastructure
## The Problem

Most households have two or three retired computers doing nothing: an old tablet, a phone with a cracked screen but a fine CPU, a laptop that's "too slow" for daily use. None of them are broken in any way that matters for a background job — they're retired because they stopped being pleasant to use as a primary device, not because they stopped being capable.

Meanwhile, the same households buy a Raspberry Pi for $60–100 to run a photo frame, an ad blocker, or a small home server — a job any of the devices already in the drawer could do.

The gap isn't hardware. It's that nobody tells you what the hardware you already own is good for, or how to put it to work without becoming a sysadmin.

## The Idea

Commodity Cloud is a toolkit that looks at a device you already own, figures out what it's actually capable of, and turns it into a single-purpose piece of infrastructure — without you needing to understand Docker, ADB, or Linux administration to get there.

The long-term shape is: discover a device → inspect what it can do → recommend a workload it's suited for → deploy it automatically. That's the full vision. It is not fully built. Below is exactly how much is real right now, and how much is roadmap.

## What's Actually Working Today

1. A real device, running a real workload, end to end. A Samsung Galaxy Tab (Android 4.0.4, 2012) runs a native photo-frame app: folder-based slideshow, shuffle, resume-last-photo, configurable transitions, OOM-safe image downsampling, immersive kiosk mode. Sideloaded via bootstrap scripts that handle dynamic port selection, VPN-aware LAN IP detection, and OS-aware firewall handling that restores itself on exit.

2. A second device, different workload. A rooted OnePlus 6T runs Pi-hole as a DNS/ad blocker — manually configured, not toolkit-driven, included to show the reuse thesis generalizes beyond one gadget.

3. A cross-platform health agent. A Python heartbeat script reports live device status (uptime, RAM, storage, workload) with platform-specific logic for Linux/macOS/Windows — built after finding and fixing a real bug where macOS "free RAM" was understated by ~10x versus Activity Monitor.

What's Designed But Not Built
Automated device discovery — currently manual.
The Inspector (auto-generates node.json) — doesn't exist yet; this is the current focus.
The Planner — rule-based on paper only, no code.
Installer, Dashboard, AI planning — not started (milestones 4–6 of 6).
Linux/Docker/Pi-hole/WireGuard automation — none scripted.

An internal review (July 2026) caught this gap directly: nine ADRs existed before any were tested against real behavior. The fix wasn't more documents — it was a rule: no design decision gets recorded without a working code artifact in the same commit.

## Current Milestone: One Device, Done for Real

### Success Criteria

Discovery — one command detects the Galaxy Tab over USB, no manual adb devices.
Inspection — a script (not a person) produces a real node.json — zero placeholder fields.
Toolkit — 3+ automation scripts (APK install, ADB-enabled check, battery-opt-exempt check) return genuine pass/fail.
Reproducibility — someone else can run discover→inspect from the README alone.
Evidence trail — at least one real bug documented with the same rigor as the macOS RAM fix.
Honest scope marker — pitch/README state plainly what's not done.
Second data point (manual, labeled) — OnePlus/Pi-hole experiment log filled in with real procedure and observations, explicitly marked manual.
Why This, Beyond the Feature List

Two things this demonstrates together: systems thinking (a domain model built around real constraints of heterogeneous, low-resource hardware — not Kubernetes vocabulary borrowed wholesale), and shipping discipline (catching an over-architecture problem mid-project and changing how the project runs, rather than writing more docs about it).
